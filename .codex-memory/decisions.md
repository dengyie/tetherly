# Decisions

## 2026-10-15 (15) - `tetherly pin` must act on the live daemon, because a PIN is process-local state
- Decision: `tetherly pin` no longer starts a node to generate a PIN. The `Cmd::Pin` variant now carries `--ui-port` (default 45716) and is a **loopback client** of the already-running daemon: it calls the new `tetherly_node::loopback_post(port, "/api/pin", b"{}")` and prints the PIN the live node armed. When nothing is listening it fails honestly (non-zero exit, message naming the port and the `tetherly --data-dir <dir> run` fix). Supporting changes: `uihttp::spawn(node, port)` → `uihttp::bind_and_spawn(node, port) -> io::Result<u16>` (binds synchronously and returns the port actually bound; a taken port is now a hard error rather than a silent `warn!`), `Node::spawn_ui()`/`Node::ui_port()` backed by a new `Shared.bound_ui: AtomicU16`, and `Node::run()` binds the UI before returning so "node up" implies the port is genuinely reachable. A regression test (`tests/phase1.rs::pin_shown_by_the_live_node_api_is_the_one_that_pairs`) POSTs `/api/pin`, pairs with the returned PIN, and also asserts a third node armed with a hardcoded PIN **cannot** be dialed, so the assertion cannot pass by accident.
- Rationale: real-device testing on the cloud phone surfaced this as the single most expensive defect of the session — hours of false diagnosis. A PIN is only meaningful to the process that holds it: `Node::generate_pin()`/`set_pin()` write `shared.pin = Some((pin, now_ms))` **in-process only**, and `session_config_inner` maps a missing PIN to `pin_created_ms = 0`, so any dial against a node that never armed a PIN is unconditionally judged `PinExpired`. The old `Cmd::Pin` did `Node::start(cfg)?; println!(node.generate_pin()?)` — it manufactured a PIN in a **second, throwaway process** whose listener nobody can reach, then exited. The symptom on the phone was "the PIN is displayed, but pairing always says expired". The correct route had always existed: the live daemon's loopback API `POST 127.0.0.1:45716/api/pin`, which is exactly what the UI's 「显示 8 位 PIN」 button uses. Making the CLI a client of that same route removes the class of bug rather than the instance.
- Alternatives considered: keep the throwaway `Node::start` but persist `pin_created_ms` so a later process could honor it (rejected — persists a secret's lifetime and its TTL to disk, and still lets two processes each think they own "the" PIN); have `tetherly pin` merely print instructions to use the UI (rejected — the CLI subcommand exists to be usable, and a short HTTP POST is a smaller surface than teaching the user a workaround); start a second long-lived node in `pin` and leave it running (rejected — two daemons on one data dir fight over ports and trust state); bind the UI lazily inside `run()` as before and have `pin` retry (rejected — the port must be real the moment `run()` reports up, or the CLI races the binder).
- Impact: `crates/tetherly-node/src/bin/tetherly.rs` (`Cmd::Pin { ui_port }` + loopback handler), `crates/tetherly-node/src/uihttp.rs` (`loopback_post` + `bind_and_spawn`), `crates/tetherly-node/src/runtime.rs` (`Shared.bound_ui`, `spawn_ui`, `ui_port`, sync bind in `run()`), `crates/tetherly-node/src/lib.rs` (`pub use uihttp::loopback_post`), `tests/phase1.rs` (+1 regression test). SSOT adds **ADR-013** and a v1.18 changelog block; `cargo test --workspace --locked` 269 → **270 green**. Verified live on two processes: `tetherly pin --ui-port 45726` printed a PIN, `POST /api/dial` with it returned `{"ok":true}`, host logged `path lan`; `tetherly pin --ui-port 45999` exits 1 with the actionable message. No wire/port/state-machine change.
- Rollback trigger: none needed for correctness (the new path is strictly more correct); to revert behavior, restore `Cmd::Pin` to the throwaway form and `uihttp::spawn` + the lazy bind — but this reintroduces the defect.
- Related files: `crates/tetherly-node/src/bin/tetherly.rs`, `crates/tetherly-node/src/uihttp.rs`, `crates/tetherly-node/src/runtime.rs`, `crates/tetherly-node/src/lib.rs`, `tests/phase1.rs`, `docs/DEVELOPMENT.md` (ADR-013, §1.18, §12 M1.1)

## 2026-10-15 (13) - Property testing extends to stateful machines via arbitrary op-programs, not model-based frameworks
- Decision: add `crates/tetherly-core/tests/state_machines.rs` (18 tests) that drive the sequence-dependent machines (`ReplayGuard`, `TokenBucket`, `NotifyLimiter`, `ClipLimiter`, `NotifyHub`, `FileHub`, `ResumeTable`, `ScreenSender`/`ScreenReceiver`/`ScreenAssembler`, `AncsIngress`) with an **arbitrary byte op-program** rather than a hand-written scenario script or a model-based framework. A `program(max_ops)` `proptest` strategy yields a `Vec<u8>` interpreted as an instruction stream: one byte selects the action, further bytes supply parameters. A `Cur` cursor wraps the program and **saturates** on out-of-range reads, so the driver itself can never panic and any panic is unambiguously the machine's fault. The safety contract is asserted **after every step**, not only at the end, so a violation is attributed to the action that caused it. Seven additional deterministic tests act as **non-vacuity witnesses** (e.g. `screen_sender_gate_opens_once_the_local_machine_consents` proves the consent gate is actually reachable), plus concrete regression cases (any-order reassembly, incomplete-stream refusal, ANCS inertness, frozen-clock dedup, accept-before-done, per-IP isolation).
- Rationale: 继续. v1.16's property layer covered **stateless** functions (decoders, round-trips). The genuinely dangerous inbound surfaces are stateful: a single input is harmless but an arbitrary *sequence* can drive the state into a contract-violating configuration. Hand-written scenarios only test the sequences the author thought of; an arbitrary op-program explores orderings the author did not. Saturation in the cursor is what makes this sound — a driver that panicked on a bad read would produce false positives indistinguishable from real machine panics.
- Alternatives considered: a model-based/proptest `StateMachineTest` harness (rejected — it requires implementing a reference model for each of 11 heterogeneous machines, which is a large amount of new code carrying its own bugs, and would make the tests harder to read than the invariants they check); random-seed or wall-clock-driven sequences (rejected — non-reproducible failures are flaky tests, not a regression net; all clocks are injected via `ManualClock`); asserting only a final invariant (rejected — loses attribution and can pass while intermediate states were invalid); asserting via a shared "operation enum" strategy instead of raw bytes (considered equally valid; raw bytes were kept because they need no per-machine strategy plumbing and reuse the v1.16 corpus idiom).
- Impact: one new test file, no production-code change, no new dependency (§13's `proptest` dev-dep from v1.16 is reused). §13's `proptest`/`fuzz` rows extended to name the stateful layer; new §1.17 changelog block; status/version → **v1.17**. **No new bug found** — v1.15's two fixes hold at the state level. `cargo test --workspace --locked` 251 → **269 green**.
- Rollback trigger: none — additive test-only file; deleting it and the §1.17 block reverts to v1.16 exactly.
- Related files: `crates/tetherly-core/tests/state_machines.rs`, `docs/DEVELOPMENT.md` §13, `.codex-memory/{project-state,todo,session-log}.md`

- Decision: implement SSOT §13's declared `proptest` and `fuzz` layers as ordinary `cargo test` targets on the **stable** toolchain. `proptest = "1"` (MIT) becomes a workspace dev-dependency; property tests live in `crates/tetherly-core/tests/decoders.rs` (27) and `crates/tetherly-net/tests/decoders.rs` (7). The §13 table row states plainly that libfuzzer/`cargo-fuzz` remains Manual-required and that the mutation driver is the stable substitute.

A deterministic seeding strategy keeps the fuzz layer a *reproducible* regression net (a failing seed reproduces exactly) rather than a coverage-guided explorer, which is an honest tradeoff given the toolchain constraint rather than a silent substitute.

## 2026-10-11 (11) - Credential-vault support is backend-per-platform, each file compile-verifiable
- Decision: `crates/tetherly-node/src/cred.rs` becomes a thin dispatcher that `#[path]`-includes one backend per target: `cred/windows.rs` (Credential Manager), `cred/macos.rs` (Keychain generic password via `security-framework`), `cred/linux.rs` (Secret Service via `secret-service`, blocking API), `cred/other.rs` (no vault → file fallback). Each backend file imports only absolute paths, so it is self-contained and can be **compile-checked for its own target from any host**. The public surface is unchanged from v1.13 (`load_or_create_identity`/`vault_store`/`vault_delete`/`vault_available`), `identity.ref` and the `identity.bin` fallback are identical across platforms, and the installed-dir-only hygiene gate (`vault_enabled_for`) is shared.
- Rationale: the user asked to continue; the last honest gap was that SSOT §6.1 named Keychain/libsecret while only Windows existed. I first probed whether these backends could be *verified* from this Windows host: `cargo check --target x86_64-apple-darwin`/`--target x86_64-unknown-linux-gnu` both work (target stds install), but the node crate can't be checked in place for those targets because the pre-existing `zstd-sys` needs a cross C compiler. Hence the `#[path]` split: a tiny probe crate (no zstd-sys) includes the exact backend file and checks it for the real target. This is not ceremony — the probe **immediately caught a real lifetime bug** in `linux.rs` (`create_item` returns `Item<'_>` borrowing the temporary `Result`, which outlives `collection` at the block tail), which would have failed the ubuntu CI job. Keeping each backend self-contained is what makes that verification possible.
- Alternatives considered: put all backends inline behind `#[cfg]` in one `cred.rs` (rejected — cannot be compile-checked off-target; the bug above would have shipped); use the `keyring` crate for cross-platform (rejected — its Linux path pulls `libdbus-sys`/C dbus headers, and it obscures the per-platform API differences); use `secret-service` `default-features` (rejected — we set `default-features=false` + `rt-tokio-crypto-rust` to avoid the `openssl` crypto backend); macOS `security-framework` item/search API (rejected — the simpler generic-password API suffices and the `errSecItemNotFound` code cleanly distinguishes absent entries).
- Impact: §6.1 storage table + paragraph rewritten ("凭据库已接 v1.13 Windows / v1.14 macOS+Linux"); new §1.14 changelog block; status/version → **v1.14**; Cargo.toml gains `[target.'cfg(target_os="macos")']` and `[target.'cfg(all(unix, not(macos)))']` deps (all MIT OR Apache-2.0, deny-clean). `unsafe` remains confined to `cred/windows.rs`; mac/Linux backends are safe-only. Tests: the vault round-trip test is gated by `TETHERLY_VAULT_TEST=1` so it runs a real keychain/Secret Service read-write on a real machine without polluting CI; `installed_data_dir_opts_into_the_vault` now runs on mac/Linux too (compile + logic).
- Rollback trigger: none — additive; removing the mac/Linux target deps reverts those platforms to the file fallback with no other change.

## 2026-10-11 (10) - Windows identity secrets live in Credential Manager; the file is the portable fallback
- Decision: on Windows, `crates/tetherly-node/src/cred.rs` stores the 64 secret bytes (`id_sk` + `n_sk`) as a **generic credential** in the per-user Credential Manager (`CredWriteW`/`CredReadW`/`CredDeleteW`, `CRED_TYPE_GENERIC`, `CRED_PERSIST_LOCAL_MACHINE`) under target `tetherly.identity:<device_id>`. The data dir keeps only `identity.ref` — a public device-id pointer (atomic, 0600) — so no key material sits in a world-readable file. `cred::load_or_create_identity` resolves the device id from `.ref` (or from a legacy `identity.bin`, which it then **migrates** into the vault and deletes from disk). Every failure mode (vault unavailable, entry missing, entry unparseable) falls back to the original file path, so startup never depends on the vault. The `unsafe` is confined to `mod ffi` (raw Win32), matching the existing `platform.rs`/`screen.rs` exemption style. **The vault is enabled only for the installed data dir** (`dir == store::default_data_dir()`), so temp-dir nodes — and therefore every integration/unit test — keep `identity.bin` in their own dir and never write the operator's real Credential Manager; `TETHERLY_VAULT=1/0` overrides.
- Rationale: SSOT §6.1 always said "系统凭据库优先" and the file was documented as the fallback, but only the file existed. Storing private keys in the OS vault is the correct protection story (the vault is per-user and protected; a `.bin` in `%LOCALAPPDATA%` is at best ACL-only). Content is unchanged — `Identity::to_bytes`/`from_bytes` — so the vault and the file hold identical material and are interchangeable, which keeps the migration and the fallback trivially correct. Gating on the installed dir is a **hygiene** decision: a machine-global vault keyed by content-derived device ids would otherwise accumulate one credential per temp test dir on every `cargo test`.
- Alternatives considered: vault-only with no file (bricks startup if the vault is ever unavailable — rejected; the file fallback keeps the node honest on any machine); storing the secret in both places always (rejected — leaves the plaintext file that the vault was meant to remove); a fixed single credential name for all dirs (rejected — collides across multiple node identities and across test dirs); enumerating the vault by prefix to find "the" identity (rejected — silently adopts a foreign identity when several exist; the `.ref` pointer is explicit and local).
- Impact: §6.1 storage table + paragraph rewritten; new §1.13 changelog block; status/version bumped to **v1.13**; Phase 6 backlog note ("Windows 凭据库于 v1.13 结项"). CI: `cred::tests::{file_fallback_roundtrips_on_every_platform, windows_vault_roundtrips_via_the_ref_pointer, installed_data_dir_opts_into_the_vault}` — the second really drives CredWrite→`.ref`→CredRead→device-id match→`identity.bin` absent→delete→not found on the Windows job; on Unix `vault_available()==false` and the file path runs.
- Rollback trigger: none — the migration is one-way but the file remains the fallback; disabling the vault (env or non-Windows) only reverts to the pre-v1.13 file behavior.
- Related files: `crates/tetherly-node/src/cred.rs`, `crates/tetherly-node/src/lib.rs`, `crates/tetherly-node/src/runtime.rs`, `crates/tetherly-node/Cargo.toml` (`Win32_Security_Credentials`), `docs/DEVELOPMENT.md` §6.1/§12

## 2026-10-11 (9) - File transfers resume across process restarts via a content-addressed id + a chunk-aligned persisted sidecar
- Decision: a file's `transfer_id` is now **content-addressed** — `"tr_" + hex(sha256(file))[..16]` — instead of a random per-transfer id, so identical bytes always map to the same id and the receiver can match its own half-written partial. The wire gains a versioned format **`TFL2`** (`magic(4) | id | total u64be | start u64be`) that carries a **start offset**; `read_header` still accepts legacy `TFL1` (start=0). The receiver writes the transfer incrementally to `inbox/.<transfer_id>.part` and, on interrupt, persists a **chunk-aligned** offset to the sidecar `inbox/.<transfer_id>.resume.json`. On Node startup `load_resume_table(data_dir)` scans `inbox/.*.resume.json` and rebuilds `ResumeTable`; the sender, when offering, asks `ResumeTable::claim(source, transfer_id, total)` and, if it returns an offset, offers with `resume_from` and — once accepted — sends **only the tail** from that offset. Resume is **hard-required to be 64 KiB chunk-aligned** because each chunk's AEAD AAD is `transfer_id || chan_offset_le` and its nonce counter is `chan_offset / CHUNK + 1`: a chunk is cryptographically pinned to its channel position and cannot be relocated across a resume boundary.
- Rationale: the SSOT (§7.4) previously said "v1 无跨进程续传" — a real gap for large files on a flaky LAN. Content addressing makes resume *safe by construction* (same bytes resume; different bytes get a different id, so we can never splice a foreign prefix onto a transfer). Binding AAD to `chan_offset` (not just the chunk index) means a resumed tail cannot be replayed at a different offset — the "cannot relocate a chunk" property is proved by unit test, not convention. Chunk alignment is what makes the nonce counter reproducible across a restart; without it the sender's counter would diverge from the receiver's open state. The `.part` + sidecar split keeps the always-in-memory design while adding durability across a crash, and the loader **drops a sidecar whose `.part` is missing or shorter than the claimed offset** (torn state) rather than promising a resume it cannot honor.
- Alternatives considered: a random transfer_id with a separate content hash exchanged in the offer (more round-trips, more state; content addressing is simpler and self-validating); resume at arbitrary byte offsets (would require per-byte AAD or a framing change and break the nonce scheme — rejected); trusting the sender's claimed `resume_from` without local validation (rejected — the receiver recomputes `claim()` from its own table: source match + size match + aligned offset in range, else `CoreError::ResumeOffset`); resuming from an unaligned/partial tail (rejected — `resumable_offset(path, chunk)` truncates the partial tail to the last full chunk).
- Impact: §7.4 rewritten (resume protocol, `TFL1`/`TFL2`); new Phase 1 milestone **M1.8**; status/version bumped to **v1.12**. core: `ResumeState`/`ResumeTable` (+`claim`/`put`), `IncomingTransfer.resume_from`, `FileHub::{offer_resumable,accept_at}`, `FileDecision.resume_from` + `accept_resuming`, `CoreError::ResumeOffset`, `FILE_CHUNK=64 KiB`. net: `TFL2`, `send_chunks_from`, `recv_chunks_after_header`, `read_header`, `resumable_offset`, `aad_for`. node: content-addressed id, incremental `.part` write with `sync_all` + `on_chunk`, `note_resume`/`clear_resume`/`resume_sidecar`, `load_resume_table`. CI: core `resume_claim_requires_source_and_size_and_alignment` + `accept_at_validates_resume_offset`; net `resume_sends_only_the_tail_from_a_chunk_boundary` + `a_chunk_cannot_be_relocated_across_resume_positions` + `resumable_offset_truncates_partial_tail`; `tests/phase1.rs::m1_8_file_resumes_from_persisted_offset` (seeds `.part`+sidecar, restarts the receiver to exercise the startup scan, asserts `resume_from == 2*64 KiB`, sha256 match, sidecar cleared).
- Rollback trigger: none — the wire change is additive and versioned (`TFL1` still decodes); reverting only loses cross-process resume, not correctness.
- Related files: `crates/tetherly-core/src/{filexfer.rs,frame.rs,error.rs,lib.rs}`, `crates/tetherly-net/src/{filechan.rs,lib.rs}`, `crates/tetherly-node/src/runtime.rs`, `tests/phase1.rs`, `docs/DEVELOPMENT.md` §7.4/§12/§13/§19

## 2026-10-11 (8) - notify.reply is deliver-only desktop→phone, consumed once from a redacted inbox
- Decision: `notify.reply` (inner type `0x0103`) carries `NotifyReply{uid, app_id, text}` (`tetherly-core::frame`), text truncated to `NOTIFY_TEXT_MAX = 4 KiB` on the multibyte-safe boundary. It is a **one-way desktop→phone** payload: the desktop composes a quick reply *against a phone notification*, and the phone (Android `NotifyListener.drainReplies()` → `fireRemoteReply()`) fires the notification's **own** `RemoteInput` reply action. The phone never synthesizes a reply the app did not declare. The inbox lives in `NotifyHub` (`tetherly-core::notify`) as `replies: HashMap<reply_id, QueuedReply>` where `reply_id = sha256(source\0app_id\0uid)`; `ingest_reply` trims, rejects blank, and is last-write-wins by `reply_id`; `take_reply_id` is **single-use** (take-once) so a reply is fired at most once. `ReplyView`/`ReplyViewDto` carry no text; `QueuedReply`'s hand-written `Debug` redacts the body (`finish_non_exhaustive`); the runtime logs only `text_len`. `MUST_UNDERSTAND` no longer applies to `0x0103`.
- Rationale: a "quick reply" is only honest if the target app declared a reply action — reusing the notification's `RemoteInput` avoids privilege escalation and fake affordances. Take-once keying prevents double-firing a reply across reconnects/UI refreshes. Keeping text out of every view/log/Debug path honors the standing no-OTP/SMS-body-in-logs rule even though this text is user-authored (it may quote a code). Deliver-only (never execute) mirrors the "never execute peer URLs" red line: the phone fires the app's own action, it does not run anything the desktop sent.
- Alternatives considered: an executed-command channel (explicitly out of scope — reply text is data, not code); bidirectional reply (phone→desktop) — not a product need and would widen the attack surface; keying the inbox by `(source,app_id,uid)` tuple directly vs a hash (chose the hash so the UI id is opaque and stable and never echoes content); storing text in the UI `Snapshot` replies list (rejected — leaks content to the UI JSON/log paths).
- Impact: §7.2 row is now `JSON:uid, app_id, text(快速回复,桌面→手机;≤4 KiB,仅投递、不执行)` instead of "stub,可忽略"; §9.6 documents the two-step (desktop compose → phone drainReplies/fireRemoteReply). CI covers `tests/phase2::m2_6_notify_reply_reaches_the_phone_and_is_consumed_once` (pair two nodes, desktop `reply_to_candidate`, phone `take_reply` once then `None`, and blank is `Err(EmptyReply)`) and `crates/tetherly-android/tests/client_e2e.rs::android_client_receives_a_quick_reply_once` (real `accept_session` server). Real on-device `RemoteInput` firing (needs notification-listener grant + a foreground notification with a reply action) is Manual-required.

## 2026-10-11 (3) - adb screen source: persistent length-prefixed PNG stream is the default; raw is opt-in
- Decision: `AdbSource` keeps ONE `adb exec-out` child per source. Default device command is `while :; do screencap -p > /data/local/tmp/.tetherly_cap<pid>; wc -c < ...; cat ...; done` — an ASCII length line then PNG bytes, binary-safe framing. `TETHERLY_ADB_RAW=1` switches to the raw RGBA_8888 loop (16-byte LE header + w*h*4) with permanent fallback to PNG if the header is not RGBA_8888. Hot-path share of the same pass: persistent zstd bulk contexts in `ZstdCodec` (Mutex), offset-based `ScreenAssembler` body, single-copy `SystemSink::present` into the DIB bits pointer, `[profile.release] lto=thin + codegen-units=1`.
- Rationale (measured on Galaxy Fold over EasyTier overlay): the adb leg moves ~187KB/s, so a raw 3.7MB frame costs 17.5s while its PNG is ~31KB (0.17s) — PNG is bandwidth-optimal on any link and raw only wins on USB/plain-LAN-class links, hence opt-in. The persistent stream removes the per-frame adb spawn (~0.3s of the ~0.9s one-shot grab); the device screencap+PNG-encode cycle (~0.44s/frame) is the new floor. Steady grab 436ms vs ~543ms one-shot. Bench 1080p/8.3MB: zstd enc 16.1→12.6ms (persistent ctx + LTO), dec 4.7→4.1ms, assembler 3.0→1.28ms (−57%, one buffer instead of per-chunk Vecs + concat copy).
- Alternatives considered: device-side gzip (toybox-only, worse ratio than PNG at same bandwidth), raw-on-LAN-by-default (needs per-link bandwidth probing — deferred), JPEG (no toybox encoder), skipping dedup (would send ~13/30 unchanged frames on a still screen).
- Impact: p95 frame-interval on a still screen now measures content-change period (dedup `Ok(None)` ticks are fast), not transport cost — do not read it as a throughput number. `bench_screen` example kept for regression checks.
- Rollback trigger: none — all changes are internal to node/core; wire format and ports unchanged.

- Related files: `crates/tetherly-crypto/src/pairbind.rs`, `docs/DEVELOPMENT.md` ADR-002

## 2026-10-09 - Trust after Noise, not after PairBind
- Decision: Write `TrustStore` only after Noise enters transport. On Noise failure, `remove` the peer. Alias is signed PairBind `device_id`, not Hello `name`.
- Rationale: Hello name/caps MITM would otherwise leave a trusted peer with a poisoned prologue.
- Alternatives considered: Commit after PairBind then rollback (TOCTOU on crash).
- Impact: First-pair Noise reads `n_pk` from Hello when trust is empty; PairBind already authenticated those keys.
- Rollback trigger: Revisit if a durable store is added before handshake completion.
- Related files: `crates/tetherly-net/src/session.rs`

## 2026-10-11 - Peer-input arithmetic must be wrap-safe (ADR-12)
- Decision: Any arithmetic in an inbound parse/reassembly path that operates on a wire value uses `saturating_add`/`checked_mul` and an explicit range check; never a bare `+`/`*` or `a - b` whose bound depends on the peer.
- Rationale: `ReplayGuard` did `msg_id + 1024` (peer `u64`) — debug panic, release wrap that weakened the replay window; `ScreenAssembler` did `total - off` from a peer `idx` — underflow = remote panic on 45720. Both are reachable by any paired peer (and, for the inner-frame path, pre-trust on the pairing socket).
- Alternatives considered: enable `overflow-checks` in release (adds cost to hot paths and only turns panic into panic, not correctness); rely on the `recent` deque / `count` guard (does not cover the single-fragment `idx` case).
- Impact: Inbound paths are total: no panic and no silently-accepted ancient id. No wire/port/state-machine change.
- Rollback trigger: None; bare peer arithmetic is a defect.
- Related files: `crates/tetherly-core/src/replay.rs`, `crates/tetherly-core/src/screen.rs`

## 2026-10-15 - Screen capture backends are self-contained files, verified per target (ADR-13)
- Decision: Each OS screen-capture/present backend lives in its own file under `crates/tetherly-node/src/screen/` (`macos.rs`, `x11.rs`), importing only absolute paths, declared from `screen.rs` with `#[cfg(...)] #[path = "screen/<os>.rs"] mod`. `SystemSource` keeps one monomorphic `inner` per target; `SystemSink::present` has one arm per target plus an honest `ScreenRefused` arm.
- Rationale: This is the `cred.rs` precedent (`cred/{windows,macos,linux,other}.rs`), and it is what makes the backends verifiable from a Windows host: a minimal probe crate that `#[path]`-includes the file compiles it for `x86_64-apple-darwin` / `x86_64-unknown-linux-gnu` with `clippy -D warnings`, catching API misuse that no amount of reading would. Extracting shared helpers into `screen.rs` would have broken that property.
- Alternatives considered: put the backends inline in `screen.rs` behind `#[cfg]` (unverifiable per target here); share stride/unpad helpers between macOS and X11 (breaks self-containment; the two differ anyway — macOS pads, X11 scanline-pads, and X11 also fills the depth-24 alpha byte).
- Impact: The `unsafe` surface grows from `cred/windows.rs` + `platform.rs` + `screen.rs::dxgi` to also include `screen/x11.rs` (raw `mmap`/`munmap`) and `screen/macos.rs` (raw pointer read of the bitmap context). Both are target-gated, documented with safety comments, and never reach `tetherly-core` (which stays `#![forbid(unsafe_code)]`).
- Honest boundary: real capture needs a real display and permission (macOS Screen Recording, an X server) and stays Manual-required; macOS present needs AppKit `NSWindow` and is refused by name; Wayland has no X11 root and reports the connection failure verbatim.
- Rollback trigger: None for the file-per-backend shape; revisit the `unsafe` scope only if a safe-Rust binding replaces `libc::mmap` or the raw context read.
- Related files: `crates/tetherly-node/src/screen.rs`, `crates/tetherly-node/src/screen/macos.rs`, `crates/tetherly-node/src/screen/x11.rs`, `crates/tetherly-node/Cargo.toml`, `docs/DEVELOPMENT.md` §9.7 / §23

## 2026-10-16 - Session liveness, bounded queues, and a glibc-2.31 release floor (ADR-14)
- Decision: (1) A session whose peer has sent nothing for `SESSION_LIVENESS_DEADLINE` (45s) is **dead**, decided by an injected clock in `tetherly-core::liveness` — never by TCP state. A 15s `ping` runs on the control session only. (2) Every session/input/screen outbound queue is **bounded** and written with `try_send`, so a slow peer produces an honest `CoreError`, never a silently accepted frame. (3) All session writes go through `ActiveSession::send_bounded` (`SESSION_WRITE_TIMEOUT=15s`, `NetError::WriteStalled`), so a full send buffer cannot park a `flush()` forever. (4) Linux release artifacts are built inside `debian:bullseye` (glibc 2.31) with a `GLIBC_2.32+` guard that fails the build.
- Rationale: The cross-VPS test found a control session that reported success forever while the peer received nothing — an `unbounded_channel` producer can never see backpressure (`send_to` "succeeded" by enqueueing), the write was `await`ed inside a `select!` branch so `flush()` parked on a full buffer, and no ping existed, so `ESTABLISHED` was mistaken for liveness. This is the v1.18 `pin` defect class again: a success claim the process cannot prove. On the release side, a dynamic binary's required `GLIBC_x.y` is a hard lower bound — flags cannot lower it; v1.20's `ubuntu-22.04` artifact required `GLIBC_2.34` and refused to start on the glibc 2.31 hosts §14 promises.
- Alternatives considered: rely on TCP `ESTABLISHED` / keepalive (proves nothing about the peer's reader; the buffer can be full while the socket is up); `unbounded_channel` + `send_timeout` (still cannot detect a stop-reading peer without a liveness clock); re-enable `SO_KEEPALIVE` tuning only (kernel-scale, minutes, not a session policy); build Linux natively on a 2.31 host (no such runner; the container is the portable equivalent).
- Impact: Heartbeat/deadline are injected and deterministic in tests; no wire-format change (`ping`/`pong` already existed). Backpressure is observable in the API error surface. The glibc floor now matches §14's coverage claim. Honest boundary: the container build is CI-only here, so the first artifact must be re-verified on a real glibc 2.31 host.
- Rollback trigger: None for liveness/backpressure (silently dropped frames are a defect). Revisit the anchor only if a reproducible older-glibc toolchain makes bullseye unnecessary.
- Related files: `crates/tetherly-core/src/liveness.rs`, `crates/tetherly-core/src/lib.rs`, `crates/tetherly-net/src/{error,session,lib}.rs`, `crates/tetherly-node/src/runtime.rs`, `.github/workflows/release.yml`, `docs/DEVELOPMENT.md` §14

## 2026-10-16 - The inner-frame payload budget is derived from the transport ceiling, not hardcoded (ADR-15)
- Decision: `tetherly-core::frame::INNER_PAYLOAD_MAX` is computed as `NOISE_MESSAGE_MAX - AEAD_TAG - INNER_HEADER` (= `65535 - 16 - 12 = 65507`), not written as `64 * 1024`. `INNER_HEADER` (= 12) is a named constant used by `InnerFrame::encode`/`decode`, and `NOISE_MESSAGE_MAX` (= 65535) records the Noise single-message cap. Every layer that sizes a payload (the screen fragment chunk, the clip-text guard) budgets against `INNER_PAYLOAD_MAX`, so none can produce a plaintext the transport refuses.
- Rationale: The old flat 64 KiB ignored the 12-byte inner header and the 16-byte AEAD tag, both of which live inside the transport's 65535-byte cap — measured (real IK handshake) to accept exactly 65519 plaintext bytes. The 29-byte overcount let the screen fragmentation emit 65536-byte fragment payloads → 65548-byte plaintext the Noise transport cannot encrypt, so **any fragmenting screen frame was unsendable**. zstd hid it on real frames. Same class as v1.18's `pin`: a success the process cannot prove. Deriving the number makes "the frame layer cannot hand the transport an unencryptable plaintext" a structural fact rather than a comment.
- Alternatives considered: keep 64 KiB and clamp at the send site (leaves `encode()` able to build an unencryptable frame; the defect can reappear on any new path); catch `Crypto(Noise("input error"))` and drop the frame (silently loses screen data — the failure we are trying to eliminate); add a `tetherly-core → tetherly-crypto` dependency to read the cap (breaks the one-way layering; core stays dependency-light and OS/crypto-free, so the number is recorded as a constant with the measurement pinned in `tetherly-crypto/tests/limits.rs`).
- Impact: Wire-compatible — no released version ever successfully sent a payload in (65507, 65536] (encryption fails before the write), so tightening the decode cap drops nothing. No port/state-machine/semantic change. The file channel (own AEAD on 45718) is untouched.
- Rollback trigger: None; a frame budget above the transport ceiling is a defect. Revisit only if the Noise transport's message cap changes (a different Noise version/pattern).
- Related files: `crates/tetherly-core/src/frame.rs`, `crates/tetherly-core/src/screen.rs`, `crates/tetherly-crypto/tests/limits.rs`, `crates/tetherly-net/tests/screen_wire.rs`, `docs/DEVELOPMENT.md` §9.7 / §14

## 2026-10-16 - The ANCS GATT transport is a dedicated thread behind a command channel, using the blocking `IAsyncOperation::get()` (ADR-16)
- Decision: `tetherly-node::ancs::win_gatt` owns **all** WinRT objects on a single dedicated `tetherly-ancs` thread that creates its own MTA apartment (`CoInitializeEx(None, COINIT_MULTITHREADED)`). The `AncsTransport` implementation the node holds is a thin front-end over a `tokio::sync::mpsc` sender of `Cmd` (`SubscribeData`/`SubscribeNotification`/`Write`/`Stop`), each carrying a one-shot reply channel; inbound GATT values cross the other way on a `tokio::sync::mpsc::unbounded_channel` of `AncsInbound`. The three synchronous port methods use `windows` 0.59's **blocking `IAsyncOperation::get()`** rather than a hand-rolled executor, and every front-end ack wait is bounded at `ACK_TIMEOUT = 10s`.
- Rationale: `AncsTransport` is `Send + Sync`, and WinRT interfaces are neither ergonomic nor cheap to move across threads; holding them on one thread and exposing only a `Sender` makes the trait bound a **structural** fact instead of an `unsafe` promise. `windows` 0.59's async extension already exposes a blocking `get()` that parks on an OS `Waiter` (no busy-wait, no spinning), so requiring a runtime/executor for a synchronous trait would add a dependency and a failure mode for nothing. Blocking until `GattWriteResult::Status == Success` turns §9.4's "Control Point is serial, one request in flight" into an observable fact rather than an assumption; the 10 s bound keeps a wedged stack from parking the node forever (the v1.21 `WriteStalled` posture — an honest error beats an unprovable success).
- Alternatives considered: (a) keep the interfaces on a tokio task and `unsafe impl Send/Sync` the wrapper — the crate's unsafe budget is spent deliberately (JNI only on desktop paths) and this would add a soundness argument for zero benefit; (b) drive the async operations with `block_on`/`futures::executor` — a new dependency plus a nested-runtime hazard, and it re-implements what the crate already ships; (c) `tokio::task::spawn_blocking` per call — the interfaces would still have to cross threads, and apartment/`Send`-ness becomes a per-call gamble; (d) fire-and-forget the Control Point write — makes seriality unprovable and would hide a wedged stack, exactly the failure class v1.18/v1.21/v1.22 all landed on.
- Impact: The node never touches a COM interface; the port stays `Send + Sync` by construction. Timeouts surface as `CoreError` (`AncsSubscribe`/`AncsWrite`) rather than a hang. Cost: one thread and one command round-trip per port call, both negligible against GATT latency. Non-Windows targets keep `open() -> Ok(None)` — honest unsupported, not a stub that pretends.
- Rollback trigger: if the blocking `get()` on a WinRT async op is ever observed to deadlock on a real device (e.g. an operation that requires the same thread's message pump), move the wait to `spawn_blocking` with the interfaces already owned by that thread. macOS/Linux stacks will follow the same shape with their own native APIs.
- Related files: `crates/tetherly-node/src/ancs.rs`, `crates/tetherly-node/src/ancs/win_gatt.rs`, `crates/tetherly-node/src/runtime.rs` (`spawn_ancs_pump`), `crates/tetherly-node/src/bin/tetherly.rs`, `tests/phase4.rs`, `docs/DEVELOPMENT.md` §9.4 / §22
